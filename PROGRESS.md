## Plan (C0)
1. Layout: `src/core/` (plain TS, no React): `rng.ts` (seeded mulberry32), `types.ts`, `estimator.ts`, `detector.ts`, `forecast.ts`, `selectors.ts` (scorecard, budget vs actual, off-plan runs, cost per capability, guardrails). `src/data/`: `generate.ts` (seed generator), `logs/*.json` + `labels.json` (hand-authored event logs and waste labels). `scripts/`: seed, backtest, eval-detector, eval-consistency (run with `tsx`).
2. Data model: `Task` exactly as in BUILD_PLAN; `EventLog { id, events: {t, kind: read|edit|command|test, file?, exitCode?, costDelta}[] }`; labels as `{logId, class, startIdx, endIdx}` spans, authored by hand.
3. Generator: ~150 tasks, 4 teams, ~3 months, lognormal costs by type x size x area, 3-4 runaways ($100-300), one hero task, one paused run, ~40 completed tasks left untagged.
4. Estimator sees features only and the training split (first 2 months); quote = percentile band of nearest similar tasks, widening + low-confidence note when matches are sparse.
5. Detector: rule-based over event logs (same command failing repeatedly with no edit between = retry loop; same file read again with no edit to it in between = repeated read); dollars saved = sum of costDelta of the redundant events.
6. Shared state: one in-memory store (React context + reducer) holding tasks, tag changes, paused-run decision, and the engineer run result. All views read via the same pure selectors in `core/selectors.ts`, so `eval:consistency` can call the identical functions in Node against a simulated sequence of actions.
7. UI: tab bar Engineer -> Leader -> CFO, global "Synthetic data" banner and global Reset. Engineer = terminal mock ("simulated session") + Try-it quote panel + log toggle. Leader and CFO = Recharts dashboards.
8. Tests: `estimator.test.ts`, `detector.test.ts` only (Vitest).

## Decisions / defaults (reversible)
- Dev deps beyond stack (approved): `tsx` to run TS scripts; also `@types/node` (typings only, for scripts).
- Historical quotes: each seeded task's `quote` is what the estimator would have said at the time, using only tasks completed before its date (`src/data/dataset.ts`). Early-July tasks get a cold-start range ($2-$40).
- Estimator: additive model in log-cost (type, size, area, developer effects fit by backfitted medians), centered on the most specific pool with >= 5 matches (type+size+area -> type+size -> type -> all); range = 10th-90th percentile from robust residual spread. Confidence is low when the type+size pool has < 5 tasks. Widening: 1.4x normal, 1.6x low, chosen by `npm run calibrate` (fit July, validate August, rule: August coverage closest to 80%).
- Generator: 148 history tasks + 1 paused run (T-149, Platform mTLS migration) + 1 hero task (T-150, Payments "Saved cards at checkout", running until the engineer view completes it). Runaways at 4 fixed positions, $100-$300. Most recent 40 completed tasks left untagged. Initiative budgets derived from non-runaway spend x 1.05-1.35.
- Try-it panel quotes from all completed tasks in the store (not only the training split); the backtest is the only place the time split applies.
- Auto-approve threshold: $25 per task (quote ceiling), in `src/core/session.ts`. Changed from the $5 per-item placeholder in the C0 plan: per-item quotes for normal work already exceed $5.
- Detector thresholds: 3+ failures of the same command with no edit anywhere between = retry loop; 3+ reads of the same file with no edit to it between = repeated read. "Dollars saved" = cost of every occurrence after the first.
- Hero session: a scripted event log (`src/data/logs.ts`, `heroScenario.ts`). Plan item ranges = the estimator's hero quote split by fixed shares (services 25%, security/perf 20%, coding 55%). Main risk = the estimator's repo-area risk. Trade-off option costs = sums of each option's event costs (surface +$0.70, platform +$4.27). Detector correction lines are generated by running `detect()` on the hero log.
- Choosing a trade-off option raises the envelope by that option's cost (engineer approval).
- Engineer Reset also restores the hero task in the store. Tabs stay mounted so the run survives tab switches; the header "Reset demo" remounts everything.
- Off-plan rule: completed runs more than $5 over their quote ceiling, plus paused or stopped runs (9 of 150 at start). Others are hidden.
- Scorecard "approved quote": a run counts as started under an approved quote if its quote ceiling is <= the $25 auto-approve threshold (or it is a scripted demo run). Runs with higher ceilings and no approval record count as uncontrolled. Control by dollars = sum of min(actual, quote ceiling) over approved runs / total spend. Result: 87.3% by task vs 37.1% by dollars, because runaways spend far past their ceilings.
- Quote accuracy tile = E1 coverage recomputed from the store (66.7%).
- Paused run (T-149): option costs from its own observed run-rate ($61.40 / 5 services done): approve all 14 (+$110.52), finish planned 6 and re-quote the rest (+$12.28), stop and revert (+$1.50 cleanup, capability not delivered, tagged "no"). Scenario text in `src/data/pausedScenario.ts`.
- Guardrails: (1) weakest repo area by quote coverage (n >= 8), recommending plan review above that area's 75th-percentile cost; (2) in-flight cap at 3x quote ceiling, citing how many runs and dollars went past it.
- CFO forecast (`src/core/forecast.ts`): weekly spend, bootstrap-resample the last 8 weeks (seeded), Q4 = 13-week sum, range = 10th-90th percentile. Starts at $1.30k-$2.23k; the chart also shows a next-week band. Forecast moves when the paused-run decision adds spend to the latest week.
- Estimate reliability = share of runs inside the quote they had at the time, by month (68% / 72% / 74%), plus the E1 backtest figure.
- Cost per capability: actual vs sum of quote ceilings ("approved"); explanation names the run furthest over its ceiling and flags runaways (> 3x ceiling). A capability is "in progress" if any of its runs is running or paused. Stopped runs are excluded and shown as "spend that delivered nothing".
- Reworded "card tokens" / "tokenization" in the hero scenario to "vaulted card references" / "card-vault" so the word "token" appears nowhere in the UI (QA F1).
- C5: added `npm run eval:forecast` (E5) as its own script; E3 replays UI actions through the shared reducer and selectors in Node. Demo story strip with Step 1/2/3 text and Next buttons. README cost-scale claim checked against data ($14.07 per developer active day, 94% under $30).

## CFO redesign (after C5)
- Data: org-scale capability aggregates (`src/data/enterprise.ts`): 190,842 modeled runs from the same per-run sampler as the history (incl. 2.7% runaway tail), $2.35M spend vs $2.79M budget. Four capabilities over budget (Refund status API: one-off incident; SCIM: recurring scope; Event pipeline backfill: no explanation; mTLS: paused, note driven by the leader's decision). Others land at 63-88% of budget. Every capability's work spreads across all 13 weeks so org spend is steady (~$170-180K/week).
- Leader and CFO totals both read `capabilityRows` (modeled + sampled tasks). The leader scorecard still uses the 150 sampled runs.
- CFO forecast = 13-week bootstrap of ongoing weekly spend (excludes one-off spend and the paused capability) + the paused capability's remaining scope by decision (pending: $0 to the full continue cost).
- "Tasks finished within budget" = share of finished sampled tasks at or under their approved quote.
